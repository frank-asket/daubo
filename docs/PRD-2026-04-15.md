# Daubo Product Requirements Document (PRD)

- **Version:** 2026-04-15
- **Status:** Latest working version (reflects implemented reliability and dashboard UX updates)

## 1) Product Goal

Daubo helps candidates run a faster, higher-quality job search with AI assistance while preserving user control over sensitive actions.

Core principle: **AI drafts and recommends; user approves before send/apply.**

## 2) Target Users

- Active job seekers managing many applications across channels
- Users needing tailored materials quickly (resume, cover letter, interview prep)
- Users wanting optional email automation without full auto-submit

## 3) Problem Statement

Candidates lose time across discovery, fit evaluation, material tailoring, and follow-up execution. Existing workflows are fragmented and prone to duplication, stale statuses, accidental double-runs, and unclear recovery when steps fail.

## 4) Product Scope (Current)

- Job discovery + fit scoring
- Application pipeline management + integrity cleanup
- Smart Prep autopilot with reliability controls
- Apply handoff with channel-aware UX (LinkedIn/company-site first, Gmail optional)
- Gmail integration for drafts (not auto-send)
- Copilot/agentic job search flow

## 5) Primary Use Cases

### UC-1: Discover and Prioritize Best-Fit Roles

- User enters role/location preferences and runs discover
- Daubo returns listings with `fit_score`, `fit_reasons`, and `risk_flags`
- User filters by minimum fit threshold and saves relevant opportunities

### UC-2: Keep Application Pipeline Clean and Actionable

- User opens Applications board and runs integrity check preview
- Daubo shows dedupe/status/stale changes before applying
- User applies cleanup and jumps directly to affected rows for review

### UC-3: Run Smart Prep Safely at Scale

- User launches Smart Prep for a batch of saved applications
- Daubo blocks overlapping runs and supports safe retries for failures
- If user double-clicks run, idempotency ensures no duplicate execution

### UC-4: Complete Channel-Aware Apply Handoff

- User generates application package and selects apply channel
- If channel is `linkedin` or company site, Gmail draft UI stays hidden
- If channel is `email` and Gmail is configured, user can draft in Gmail and send manually

### UC-5: Recover Quickly from Integration Issues

- If Gmail status/disconnect fails, user sees a clear actionable error
- User can refresh Gmail status directly from handoff flow
- User continues with non-Gmail channels when email path is unavailable

## 6) Functional Requirements

### Discovery and Match

- Return listing-level:
  - `fit_score` (1.0 to 5.0)
  - `fit_reasons` (explainability bullets)
  - `risk_flags` (review caveats)
- Dashboard surfaces sort/filter by fit score in discovery panels

### Application Pipeline Integrity

- Endpoint to run integrity checks with:
  - Dry-run preview mode
  - Apply mode
- Integrity pass supports:
  - Deduplication rules
  - Status normalization rules
  - Stale item detection
- UI shows summary and per-change details with row jump actions

### Smart Prep Reliability

- Prevent overlapping autopilot runs server-side
- Support retry scopes:
  - `failed_only`
  - `gmail_failed_only`
- Return item-level diagnostics:
  - status category
  - retryability
  - suggested action
  - latency

### Idempotency Contract (Autopilot Run)

- `POST /v1/me/autopilot/run` accepts `Idempotency-Key`
- Same key + same payload fingerprint replays prior result
- Same key + different payload is rejected (`409 Conflict`)
- Same key + unverifiable previous payload is rejected (`409 Conflict`)

### Gmail and Handoff UX

- Gmail connect card shows user-facing errors for status/disconnect failures
- Apply handoff can manually refresh Gmail status
- Gmail draft block appears only for `email` apply channel
- LinkedIn/channel flows do not surface unnecessary Gmail draft UI

## 7) Non-Functional Requirements

- Reliability first: idempotent, concurrency-safe operations
- Explainability for AI scoring outputs
- Human-in-the-loop controls for outbound actions
- Safe incremental schema evolution for production

## 8) API and Data Contract Highlights

- `POST /v1/me/autopilot/run`
  - Idempotency-aware response behavior
  - Typed conflict detail payload
- `POST /v1/me/applications/integrity-check`
  - dry-run/apply modes
  - machine-readable change report
- Discovery schemas include fit annotations
- Autopilot persistence includes idempotency key and request fingerprint

## 9) Success Metrics

- Fewer duplicate or stale applications in the pipeline
- Fewer accidental overlapping Smart Prep runs
- Better retry recovery rate for failed run items
- Lower UX confusion around Gmail availability and channel gating
- Faster time from discovery to ready-to-apply package

## 10) Known Risks and Current Gaps

- Local QA can be blocked by auth verification setup in dev
- Local backend runtime mismatch can block full-stack testing if Python version is outside dependency support range
- Additional endpoint-level tests still needed for overlap + idempotency interaction ordering

## 11) Near-Term Roadmap

- Add integration tests for autopilot overlap/idempotency sequencing
- Add run-history observability (replayed vs fresh run)
- Continue dashboard hardening for blocked states (auth/backend/integration outages)
